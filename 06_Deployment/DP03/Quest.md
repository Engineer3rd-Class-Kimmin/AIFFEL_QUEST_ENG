# 체크포인트 문제와 답

## 1. async/await 기본 원리 체크포인트

### Q1. `time.sleep(3)`과 `await asyncio.sleep(3)`의 핵심 차이는 무엇입니까?

`time.sleep(3)`은 실행 중인 스레드를 3초 동안 멈추는 **동기 블로킹 작업**입니다.  
FastAPI의 이벤트 루프에서 실행되면 그동안 다른 요청을 처리할 수 없습니다.

반면 `await asyncio.sleep(3)`은 3초 동안 기다려야 한다는 사실을 이벤트 루프에 등록한 뒤,  
그 대기 시간 동안 이벤트 루프가 **다른 작업을 처리할 수 있도록 제어권을 넘깁니다.**

즉,

```text
time.sleep(3)
→ 현재 스레드를 막음
→ 다른 작업을 처리하지 못함

await asyncio.sleep(3)
→ 대기만 등록하고 제어권 반환
→ 대기 중 다른 작업 처리 가능
```

---

### Q2. 모델 추론처럼 CPU를 계속 사용하는 작업에서 `async/await`만으로 동시 처리가 안 되는 이유는 무엇입니까?

`async/await`는 작업이 `await` 지점에서 제어권을 이벤트 루프에 돌려줄 때 효과가 있습니다.

하지만 모델 추론처럼 CPU를 계속 사용하며 계산하는 **동기 작업**은 실행 중간에 자동으로 제어권을 반환하지 않습니다.  
따라서 `async def` 안에서 모델 추론을 직접 실행하면, 추론이 끝날 때까지 이벤트 루프가 계속 점유됩니다.

즉, 단순히 함수 앞에 `async`를 붙인다고 CPU 연산 자체가 자동으로 비동기가 되는 것은 아닙니다.

---

## 2. 동기 추론 문제 체크포인트

### Q1. `async def` 안에서 `time.sleep(3)`을 호출하면 왜 다른 요청까지 지연됩니까?

`async def` 엔드포인트는 이벤트 루프에서 실행됩니다.

그 안에서 `time.sleep(3)` 같은 동기 블로킹 함수를 호출하면 이벤트 루프 자체가 3초 동안 멈춥니다.  
이벤트 루프가 멈춰 있는 동안에는 다른 API 요청이나 헬스체크 요청도 처리할 수 없습니다.

```text
async def 엔드포인트
    ↓
time.sleep(3)
    ↓
이벤트 루프 3초 정지
    ↓
다른 요청 처리 불가
```

---

### Q2. 일반 `def`로 선언된 엔드포인트는 FastAPI가 내부적으로 어떻게 처리합니까?

일반 `def`로 선언된 엔드포인트는 FastAPI가 기본 스레드풀에서 실행합니다.

따라서 해당 함수 안에서 `time.sleep()`이나 동기 추론을 수행하더라도  
이벤트 루프 자체는 직접 막히지 않으므로 다른 요청을 계속 처리할 수 있습니다.

다만 기본 스레드풀의 크기에는 제한이 있고, 다른 동기 엔드포인트들과 같은 스레드풀을 공유한다는 한계가 있습니다.

---

### Q3. blocking 추론 중 헬스체크까지 막히면 실무에서 어떤 문제가 발생할 수 있습니까?
 
로드밸런서나 운영 시스템은 헬스체크 응답을 보고 서버가 정상인지 판단하는 경우가 많습니다.

추론 때문에 이벤트 루프가 막혀 헬스체크에 응답하지 못하면 실제 서버가 살아 있어도  
로드밸런서가 서버를 **비정상 또는 다운 상태로 오인**할 수 있습니다.

그 결과 정상 서버가 트래픽 처리 대상에서 제외되는 문제가 발생할 수 있습니다.

---

## 3. `run_in_executor` 체크포인트

### Q1. `run_in_executor`가 이벤트 루프 블로킹을 방지하는 원리는 무엇입니까?

`run_in_executor`는 동기 함수를 이벤트 루프에서 직접 실행하지 않고  
**별도의 스레드 또는 프로세스에서 실행하도록 위임**합니다.

이벤트 루프는 해당 작업이 진행되는 동안 다른 요청을 처리할 수 있고,  
작업이 끝나면 `await`를 통해 결과를 받아옵니다.

```python
result = await loop.run_in_executor(
    executor,
    func,
    arg,
)
```

동작 순서는 다음과 같습니다.

1. `func(arg)`를 별도 실행 공간에 맡깁니다.
2. 이벤트 루프는 다른 요청을 처리합니다.
3. `func` 실행이 끝나면 결과를 받아옵니다.

---

### Q2. `run_in_executor`의 첫 번째 인자에 `None`을 넣으면 어떤 스레드풀이 사용됩니까?

첫 번째 인자에 `None`을 넣으면 **기본 스레드풀**이 사용됩니다.

추론 전용 스레드풀을 사용하고 싶다면 `ThreadPoolExecutor`를 직접 만든 뒤 첫 번째 인자로 전달합니다.

---

### Q3. 일반 `def`와 `async def + run_in_executor`의 핵심 차이는 무엇입니까?

둘 다 동기 작업 때문에 이벤트 루프가 직접 막히는 것을 피할 수 있지만, 스레드풀 제어 방식이 다릅니다.

**일반 `def`**

- FastAPI의 기본 스레드풀을 사용합니다.
- 스레드풀을 다른 엔드포인트와 공유합니다.
- 추론용 스레드풀 크기를 직접 세밀하게 제어하기 어렵습니다.

**`async def + run_in_executor`**

- 추론 전용 `ThreadPoolExecutor`를 직접 만들 수 있습니다.
- `max_workers`를 직접 설정할 수 있습니다.
- 추론 부하와 다른 엔드포인트의 작업을 분리할 수 있습니다.

따라서 단순한 서비스에서는 일반 `def`도 사용할 수 있지만,  
추론 작업의 동시 실행 수를 명시적으로 관리하려면 `run_in_executor` 방식이 유리합니다.

---

### Q4. GPU 추론 시 스레드풀 크기를 1~2로 제한하는 이유는 무엇입니까?
  
GPU 추론은 GPU 메모리의 영향을 크게 받으며, GPU 자체가 내부적으로 병렬 연산을 수행합니다.

따라서 스레드 수를 많이 늘려도 처리 속도가 크게 향상되지 않을 수 있고,  
오히려 여러 추론이 동시에 GPU 메모리를 사용하면서 메모리 부족 문제가 발생할 수 있습니다.

그래서 노트북에서는 GPU 추론 시 스레드풀 크기를 보통 **1~2 정도로 제한**하도록 안내합니다.

## 4. 에러 핸들링과 로깅 체크포인트

### Q1. 글로벌 Exception Handler를 사용하면 어떤 반복을 줄일 수 있습니까?

각 엔드포인트마다 동일하거나 비슷한 `try/except` 예외 처리 코드를 반복해서 작성하는 것을 줄일 수 있습니다.

글로벌 Exception Handler를 사용하면 공통 예외를 한 곳에서 중앙 처리할 수 있습니다.

즉,

```text
각 API마다 try/except 반복
        ↓
글로벌 Exception Handler 하나로 공통 처리
```

---

### Q2. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는 무엇입니까?

스택 트레이스에는 내부 코드 경로, 사용 중인 라이브러리, 구현 구조, 원본 오류 정보 등이 포함될 수 있습니다.

이 정보가 외부 클라이언트에게 노출되면 시스템 내부 구조를 파악하는 데 이용될 수 있어 **보안 위험**이 생깁니다.

따라서 상세 오류는 서버 로그에 기록하고, 클라이언트에게는  
`"서버 내부 오류가 발생했습니다"`와 같은 안전한 메시지만 반환하는 것이 좋습니다.

---

### Q3. `logging` 모듈이 `print()`보다 나은 점은 무엇입니까?

`logging`은 단순 문자열 출력보다 운영 환경에서 필요한 정보를 체계적으로 기록할 수 있습니다.

노트북에서 제시한 주요 장점은 다음과 같습니다.

- 시간 정보 기록
- 로그 심각도 구분
- 모듈 이름 표시
- `INFO`, `WARNING`, `ERROR`, `CRITICAL` 등 로그 레벨 사용
- 필요하면 파일이나 외부 로그 서비스로 확장 가능

## Q1. 동기 서버에서 3초 걸리는 추론을 3명이 동시에 요청하면 총 몇 초 걸립니까?

약 **9초** 걸립니다.

동기 블로킹 방식에서는 요청을 한 번에 하나씩 순차 처리하므로,

```text
첫 번째 요청: 3초
두 번째 요청: 3초
세 번째 요청: 3초

총 3 + 3 + 3 = 약 9초
```

가 됩니다.

## Q2. `time.sleep(3)`과 `await asyncio.sleep(3)`의 핵심 차이는?

`time.sleep(3)`은 현재 실행 스레드를 멈추는 동기 블로킹 작업이고,  
`await asyncio.sleep(3)`은 기다리는 동안 이벤트 루프가 다른 작업을 처리할 수 있도록 제어권을 반환합니다.

---

## Q3. `async def` 안에서 동기 블로킹 코드를 실행하면 왜 헬스체크까지 영향받습니까?

`async def` 엔드포인트가 실행되는 이벤트 루프에서 동기 블로킹 코드가 직접 실행되기 때문입니다.

이벤트 루프가 블로킹 작업이 끝날 때까지 멈추므로  
같은 이벤트 루프가 처리해야 하는 헬스체크 요청도 기다리게 됩니다.

---

## Q4. `run_in_executor`가 이벤트 루프 블로킹을 방지하는 원리는?

무거운 동기 작업을 별도 스레드 또는 실행기에 맡기고,  
이벤트 루프는 그동안 다른 요청을 처리하도록 하기 때문입니다.

작업이 끝나면 `await`를 통해 결과만 받아옵니다.

---

## Q5. 글로벌 Exception Handler를 사용하는 이유는?

각 엔드포인트에서 반복되는 예외 처리 코드를 줄이고,  
서버 전체의 예외를 중앙에서 일관되게 처리하기 위해 사용합니다.

또한 상세 오류는 서버 로그에 남기고 클라이언트에는 안전한 오류 메시지만 반환하는 구조를 만들 수 있습니다.

---

## Q6. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는?

스택 트레이스에 내부 코드 구조, 파일 경로, 라이브러리 정보, 원본 오류 등이 포함될 수 있어  
외부에 노출될 경우 보안 위험이 있기 때문입니다.

상세 오류는 서버 로그에 기록하고, 외부에는 필요한 최소한의 오류 정보만 제공해야 합니다.
