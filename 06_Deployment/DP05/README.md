- [x] **2. 전체 코드에서 가장 핵심적이거나 가장 복잡하고 이해하기 어려운 부분에 작성된 주석 또는 doc string을 보고 해당 코드가 잘 이해되었나요?**

    네. 핵심 코드에 함수와 클래스의 역할을 설명하는 doc string과 주석이 비교적 잘 작성되어 있었습니다.

    가장 핵심적인 부분은 `HousingPredictor` 클래스라고 생각합니다.

    이 클래스는 단순히 모델 추론만 수행하는 것이 아니라,

    1. 전처리 파라미터 로드
    2. 모델 가중치 로드
    3. 입력 피처 순서 정렬
    4. 정규화
    5. Tensor 변환
    6. PyTorch 추론
    7. 실제 가격 단위 변환

    을 하나의 클래스 안에서 처리하고 있습니다.

    특히 다음 주석이 코드 이해에 도움이 되었습니다.

    ```python
    # 피처를 올바른 순서로 배열
    values = [features[name] for name in self.feature_names]

    # 정규화
    normalized = (values - self.mean) / self.std

    # 추론
    with torch.no_grad():
        output = self.model(input_tensor)
    ```

    또한 `predict()` 함수에는 입력과 반환값을 설명하는 doc string이 작성되어 있어,
    함수의 역할과 데이터 흐름을 이해하기 쉬웠습니다.

    FastAPI 부분에서도

    ```python
    # 추론 전용 스레드풀
    inference_executor = ThreadPoolExecutor(max_workers=4)
    ```

    과

    ```python
    result = await loop.run_in_executor(
        inference_executor,
        predictor.predict,
        features,
    )
    ```

    코드가 모델 추론을 별도 스레드에서 처리하기 위한 목적이라는 점이 주석으로 표현되어 있어 이해에 도움이 되었습니다.

    **근거로 캡처하기 좋은 부분**
    - `HousingPredictor.predict()` 함수
    - `ThreadPoolExecutor` + `run_in_executor` 코드


- [x] **3. 에러가 난 부분을 디버깅하여 문제를 해결한 기록을 남겼거나 새로운 시도 또는 추가 실험을 수행해봤나요?**

    네. 다양한 에러 상황과 추가적인 통합 테스트를 수행한 점이 좋았습니다.

    특히 API가 정상 입력만 처리하는 것이 아니라 다음과 같은 잘못된 입력에 대해서도 테스트하였습니다.

    - 필수 필드 누락
    - Latitude 범위 초과

    또한 단순한 정상 요청 테스트를 넘어서

    8개의 요청이 모두 약 2초 내외에 HTTP 200으로 완료되었고,
    전체 요청도 약 2.05초에 처리된 결과를 통해 비동기 처리 구조가 정상적으로 작동하는지 검증하였습니다.

    다만 실제 에러 발생 당시의
    `문제 발생 → 원인 분석 → 코드 수정 → 재실행`
    과정이 별도의 디버깅 기록으로 더 명확하게 정리되어 있었다면 더욱 좋았을 것 같습니다.

- [x] **5. 코드가 간결하고 효율적인가요?**

    전체적으로 기능별로 코드가 잘 분리되어 있어 비교적 간결하고 유지보수하기 좋은 구조입니다.

    특히 다음과 같이 역할별로 분리한 점이 좋았습니다.

    ```text
    housing_model.py
        → 모델 정의 및 추론

    housing_schemas.py
        → Pydantic 요청/응답 스키마

    housing_api.py
        → FastAPI 서버 및 엔드포인트

    app_housing.py
        → Streamlit 프론트엔드
    ```

    또한 반복적으로 필요한 기능을 함수나 클래스로 묶어 사용했습니다.

    예를 들면

    - `HousingPredictor`
    - `call_api()`
    - `run_streamlit()`
    - `show_dashboard()`
    - `send_predict()`

    등이 각각 역할별로 분리되어 있어 코드의 재사용성과 가독성이 좋았습니다.

    모델 추론에 `ThreadPoolExecutor`를 별도로 사용한 점도
    FastAPI 이벤트 루프의 블로킹을 줄이기 위한 효율적인 구조라고 생각합니다.

    개선할 점으로는 서버 실행 도우미와 포트 확인 함수가 여러 위치에서 비슷하게 사용되고 있어,
    공통 utility 모듈로 분리하면 코드 중복을 조금 더 줄일 수 있을 것 같습니다.


# 회고(참고 링크 및 코드 개선)

이번 코드 리뷰를 통해 모델 배포에서는 단순히 모델 정확도만 중요한 것이 아니라
전처리 재현성, API 입력 검증, 예외 처리, 동시 요청 처리,
프론트엔드 연결까지 함께 고려해야 한다는 점을 확인할 수 있었습니다.

특히 학습 시 사용한 `mean`, `std`, `feature_names`를 모델 가중치와 함께 저장하고,
실제 추론에서도 동일하게 사용하는 구조가 인상적이었습니다.

또한 정상 요청뿐만 아니라 잘못된 입력과 동시 요청까지 테스트하여
서비스 관점에서 모델을 검증한 점이 좋았습니다.

추가적으로 개선한다면 다음과 같은 부분을 고려할 수 있을 것 같습니다.

1. 실제 디버깅 과정의 문제 원인과 해결 과정을 별도 기록
2. 모델 성능 개선 실험 및 비교
3. API Key 인증 적용
4. Docker를 이용한 실행 환경 통일
5. 모델 및 전처리 파일의 버전 관리

전체적으로 **모델 학습 → 전처리 저장 → FastAPI → Streamlit → 통합 테스트**까지
End-to-End 모델 배포 흐름을 잘 구현한 프로젝트라고 생각합니다.
