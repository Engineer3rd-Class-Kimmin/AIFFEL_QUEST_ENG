# 1. 프로젝트 실행 내역 캡처 및 설명  

이번 프로젝트에서는 Hugging Face 기반의 사전학습 모델을 활용하여 사용자가 입력한 텍스트를 분류하는 AI 서비스를 구현하였다.  
전체 서비스는 크게 **모델 추론 기능, FastAPI 백엔드 서버, API Key 인증, Pydantic 입력 검증, 비동기 추론 처리, Streamlit 프론트엔드**로 구성하였다.  

먼저 `model_service.py`에서 사용할 모델을 로드하고 실제 예측을 수행하는 기능을 구현하였다.  
서버가 시작되면 모델을 한 번 로드하여 메모리에 유지하도록 구성하였으며,  
사용자의 요청이 들어올 때마다 모델을 새로 불러오는 방식이 아니라 이미 로드된 모델을 사용해 추론하도록 하였다.  
이를 통해 반복 요청 시 모델 로딩 시간을 줄이고 보다 효율적으로 예측을 수행할 수 있도록 하였다.  

입력과 출력 데이터는 `schemas.py`에서 Pydantic 모델로 정의하였다.  
사용자가 입력하는 텍스트는 `PredictRequest`를 통해 검증하며, 빈 문자열이나 잘못된 형식의 데이터가 모델까지 전달되지 않도록 하였다.  
예측 결과는 `PredictResponse` 형태로 반환하여 결과값의 구조를 일정하게 유지하도록 구성하였다.  

FastAPI 서버에서는 `/health`와 `/predict` 엔드포인트를 구현하였다.  
`/health`는 현재 서버가 정상적으로 실행되고 있는지와 모델이 정상적으로 로드되었는지를 확인하기 위한 용도로 사용하였다.  
캡처 화면에서 `status` 값과 `model_loaded` 상태가 정상적으로 반환되는 것을 통해 FastAPI 서버와 모델이 정상적으로 실행되고 있음을 확인하였다.  

`/predict` 엔드포인트에서는 사용자가 전달한 텍스트를 받아 AI 모델의 예측 결과를 반환하도록 구현하였다.  
해당 API에는 `Depends(verify_api_key)`를 적용하여 API Key를 입력한 사용자만 예측 기능을 사용할 수 있도록 하였다.  
이를 통해 인증되지 않은 사용자의 무분별한 API 호출을 방지하고 기본적인 접근 제어가 가능하도록 구성하였다.  

또한 모델 추론은 일반적인 동기 작업이기 때문에 FastAPI의 이벤트 루프를 직접 점유하지 않도록 `run_in_executor`와 `ThreadPoolExecutor`를 사용하였다.  
예측 작업을 별도의 스레드에서 처리함으로써 모델 추론이 진행되는 동안에도 서버가 다른 요청을 처리할 수 있는 구조로 작성하였다.  
이를 통해 단순히 모델을 실행하는 것뿐만 아니라 실제 API 서비스에서 고려해야 하는 비동기 처리 구조도 적용해 보았다.  

서버 실행 후 Swagger UI를 통해 API가 정상적으로 동작하는지 확인하였다.  
`/health` 요청을 통해 서버 상태를 확인하고, `/predict` 요청에서는 API Key와 테스트용 텍스트를 입력하여 실제 예측 결과가 반환되는지 테스트하였다.  
정상적인 API Key를 사용한 경우에는 모델의 분류 결과와 신뢰도 값이 반환되었으며,  
잘못된 인증 정보가 사용될 경우 요청이 거부되도록 하여 인증 기능도 정상적으로 동작하는 것을 확인하였다.  

사용자가 보다 쉽게 서비스를 사용할 수 있도록 Streamlit을 이용한 웹 프론트엔드도 구현하였다.  
Streamlit 화면에서는 사이드바에서 FastAPI 서버 주소와 API Key를 입력할 수 있도록 하였고,  
메인 화면에서는 분석할 텍스트를 직접 입력할 수 있도록 구성하였다.  
사용자가 `예측하기` 버튼을 누르면 `requests.post()`를 이용해 FastAPI의 `/predict` 엔드포인트로 요청을 전송하도록 하였다.  

FastAPI 서버에서 반환된 결과는 Streamlit 화면에서 분류 결과와 신뢰도로 표시하였다.  
신뢰도는 백분율과 진행 막대 형태로 시각화하여 사용자가 결과를 쉽게 확인할 수 있도록 하였으며,  
필요할 경우 전체 JSON 응답도 확인할 수 있도록 구성하였다.  
이를 통해 모델의 추론 기능이 백엔드에서만 동작하는 것이 아니라 실제 사용자가 웹 화면을 통해 입력하고 결과를 확인할 수 있는 하나의 서비스 형태로 완성되었다.  

최종적으로 실행 화면을 통해 **Streamlit 사용자 입력 → FastAPI API 요청 → API Key 검증 → Pydantic 입력 검증 → AI 모델 추론 → 예측 결과 반환 → Streamlit 결과 출력**의 전체 흐름이 정상적으로 연결되는 것을 확인하였다.  

이번 프로젝트를 통해 단순히 머신러닝 모델을 노트북에서 실행하는 것에서 나아가,  
모델을 별도의 서비스 모듈로 분리하고 FastAPI를 이용해 API로 제공한 뒤 Streamlit 프론트엔드까지 연결하는 전체 과정을 구현하였다.  
또한 입력 검증, API 인증, 비동기 추론, 예외 처리와 같은 실제 AI 서비스에 필요한 기본적인 요소들을 함께 적용하여 하나의 완성된 AI 웹 서비스를 구성할 수 있었다.

# Day 8 최종 체크포인트 답변

**Q1. 본인의 프로젝트에서 Pydantic 검증은 어떤 잘못된 입력을 막아줍니까?**

본 프로젝트의 `PredictRequest`에서는 `text` 필드를 문자열(`str`)로 정의하고, `min_length=1`, `max_length=5000` 조건을 적용했습니다.  
따라서 `text` 필드가 누락된 요청, 문자열이 아닌 잘못된 형식의 입력, 빈 문자열, 그리고 5,000자를 초과하는 지나치게 긴 입력을 API 단계에서 차단할 수 있습니다.  
이 검증을 통해 잘못된 데이터가 모델 추론 함수까지 전달되는 것을 막고, 서버가 예측 가능한 입력만 처리하도록 할 수 있습니다.

**Q2. `Depends(verify_api_key)`를 제거하면 어떤 위험이 있습니까?**

`Depends(verify_api_key)`를 제거하면 `/predict` 엔드포인트를 누구나 인증 없이 호출할 수 있게 됩니다.  
그러면 외부 사용자가 API를 무제한으로 호출하여 서버의 CPU/GPU 자원을 소모할 수 있고, 과도한 요청으로 서비스가 느려지거나 중단될 위험도 있습니다.  
현재 프로젝트에서는 `X-API-Key` 헤더의 값을 검사하여 등록된 사용자만 추론 API를 사용할 수 있도록 제한하고 있으므로, 해당 인증 로직은 서비스 접근 통제에 필요합니다.

**Q3. `run_in_executor`를 사용한 이유는 무엇입니까?**

모델의 `predict()` 함수는 일반적인 동기 함수이며, 모델 추론에는 일정 시간이 걸릴 수 있습니다.  
FastAPI의 비동기 엔드포인트 안에서 이 함수를 그대로 실행하면 추론이 끝날 때까지 이벤트 루프가 점유되어 다른 요청 처리에 영향을 줄 수 있습니다.  
따라서 `run_in_executor`를 사용해 모델 추론 작업을 `ThreadPoolExecutor`의 별도 스레드에서 실행하고, FastAPI의 이벤트 루프가 다른 요청을 계속 처리할 수 있도록 구성했습니다.

**Q4. Day 1~8 중 가장 많이 참고한 Day는 어디였습니까? 왜?**

가장 많이 참고한 부분은 **Day 5와 Day 6**입니다.  
Day 5에서는 모델 서비스와 FastAPI 서버를 연결하는 구조, Request/Response 스키마, API 엔드포인트 구성, Streamlit UI에서 API를 호출하는 방법을 참고했습니다.  
Day 6에서는 `API Key` 인증과 `Depends()`를 이용해 보호된 엔드포인트를 구성하는 방법을 참고했습니다.  
이번 프로젝트는 모델 자체를 새로 학습하는 것보다 이미 학습된 Hugging Face 모델을 실제 API와 웹 UI로 서비스하는 것이 핵심이었기 때문에 이 두 Day의 내용이 가장 직접적으로 활용되었습니다.

**Q5. 이 서비스를 실제로 배포하려면 추가로 무엇이 필요합니까?**

현재 프로젝트는 로컬 환경에서 동작하는 데모 서비스이므로 실제 배포를 위해서는 몇 가지 요소가 추가로 필요합니다.  
먼저 FastAPI와 Streamlit을 실행할 서버 또는 클라우드 환경이 필요하며, `requirements.txt`와 같은 의존성 관리 및 Docker를 이용한 실행 환경 표준화가 필요합니다.  
또한 현재 코드에 직접 등록된 API Key 대신 환경변수나 Secret Manager를 이용해 인증 정보를 안전하게 관리해야 합니다.  
외부 서비스를 위해서는 HTTPS 적용, 도메인 연결, 요청 제한(Rate Limiting), 로그 및 모니터링, 예외 처리 강화도 필요합니다.  
마지막으로 코드 변경 시 자동으로 테스트와 배포가 이루어지도록 CI/CD 파이프라인을 구성하면 실제 운영에 더 적합한 서비스가 됩니다.

# 프로젝트 회고

이번 프로젝트를 통해 단순히 머신러닝 모델을 실행하는 것에서 끝나는 것이 아니라, **모델을 실제 서비스 형태로 연결하는 전체 과정**을 경험할 수 있었습니다.  

가장 의미 있었던 부분은 Hugging Face의 사전학습 모델을 불러온 뒤,  
이를 `model_service.py`에서 추론 함수로 분리하고 FastAPI의 `/predict` 엔드포인트와 연결한 과정이었습니다.  
이전에는 모델의 성능이나 예측 결과 자체에 집중했다면, 이번에는 모델이 실제 사용자 요청을 받아 안정적으로 응답하려면  
API 구조, 입력 검증, 인증, 예외 처리 같은 요소도 중요하다는 점을 알게 되었습니다.  

특히 Pydantic 스키마를 사용해 입력값을 검증하면서, 잘못된 데이터가 모델 내부까지 들어가기 전에 API 단계에서 차단할 수 있다는 점을 이해하게 되었습니다.  
또한 `Depends(verify_api_key)`를 이용해 API Key 인증을 적용하면서,  
실제 서비스에서는 누구나 무제한으로 모델을 호출할 수 없도록 접근 제어가 필요하다는 점도 배웠습니다.  

`run_in_executor`를 적용한 부분도 인상적이었습니다.  
모델 추론은 동기적으로 실행되는 작업이기 때문에 FastAPI의 이벤트 루프 안에서 그대로 실행하면 다른 요청 처리에 영향을 줄 수 있습니다.  
이를 별도 스레드에서 실행함으로써 비동기 서버 구조와 모델 추론을 함께 사용하는 방법을 익힐 수 있었습니다.  

Streamlit 프론트엔드를 만들면서는 백엔드와 프론트엔드가 실제로 어떻게 연결되는지도 확인할 수 있었습니다.  
사용자가 텍스트를 입력하고 API Key를 넣은 뒤 버튼을 누르면 `requests.post()`를 통해 FastAPI 서버로 요청이 전달되고,  
반환된 분류 결과와 confidence 값이 화면에 표시되는 흐름을 직접 구현했습니다.  
이를 통해 하나의 AI 기능이 사용자에게 전달되기까지 모델, API, 인증, UI가 서로 연결되어야 한다는 점을 체감했습니다.  

진행 중 가장 어려웠던 점은 각 파일의 함수명과 클래스명이 서로 정확히 맞아야 한다는 점이었습니다.  
예를 들어 `main.py`에서 `PredictRequest`를 import하더라도 `schemas.py`에 해당 클래스가 정의되어 있지 않으면 서버 자체가 시작되지 않았습니다.  
처음에는 개별 파일만 작성하면 된다고 생각했지만,  
실제로는 `auth.py`, `schemas.py`, `model_service.py`, `main.py`, `frontend/app.py`가 하나의 시스템처럼 맞물려 동작해야 한다는 것을 알게 되었습니다.  

이번 프로젝트를 통해 AI 모델을 단순히 노트북에서 테스트하는 단계와 실제 서비스로 제공하는 단계 사이에는 생각보다 많은 차이가 있다는 것을 배웠습니다.  
앞으로 실제 배포까지 확장한다면 환경변수를 이용한 비밀정보 관리, HTTPS, Docker, 요청 제한, 로그 및 모니터링, CI/CD 같은 요소도 추가해 보고 싶습니다.  

전체적으로 이번 프로젝트는 **머신러닝 모델을 API와 웹 UI로 연결해 하나의 작은 AI 서비스를 완성했다는 점**에서 의미가 있었습니다.  
앞으로는 모델 정확도뿐 아니라 사용성, 안정성, 보안, 배포 구조까지 함께 고려하는 방향으로 프로젝트를 발전시키고 싶습니다.
